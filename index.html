第一部分 · PRD
§ 01

需求背景

超体社区现在有 1,000+ 会员，主要是 CXO、创业者、私募金融这条线的人。丹尼在《超体》邀请信里已经讲得很清楚：这些人都有至少一个值得被 AI 放大的生产函数，对他们来说，最稀缺的资源不是钱，是注意力和精力。

但现实是，公司的项目管理日常，恰恰是吃掉注意力最多的地方。追进度、读周报、在十几个飞书群里翻关键信息、惦记着哪个供应商还等着你拍板——这些事重复又低杠杆，却实实在在耗掉一个决策者最宝贵的那点精力。

PM 判断（关键洞察） 现有的项目管理工具（飞书项目、Asana、Jira）死因都一样：它们要人把数据喂进去。管理者没空填，下属嫌麻烦不填，工具慢慢就成了摆设。所以 PMO 的第一性原理不是做一块更好看的看板，而是零录入、自动抓取、主动汇报——把 PMO 从一套流程软件，变成一位会主动操心的同事。
§ 02

目标用户

P0 — 创始人 / CXO（核心）

一个人扛多项目决策，信息严重过载，天天在当人肉信息汇总器。他们要的不是更多报表，而是今天到底有哪几件事需要你拍板，以及每件事背后的来龙去脉。

P1 — 创业公司管理者 / 项目负责人

带 5–50 人的团队，周报、对齐进度、向上报风险一样不少，还经常被上面（也就是 P0 那群人）嫌汇报跟不上、信息有截留。

P2 — 私募 / 金融从业者

盯投后项目和尽调进度，对投入产出特别敏感，最难受的是十几个标的并行推进时，靠人记不住哪个出了岔子。

§ 03

把 Founder 从追进度这种低杠杆的事里解放出来，让 AI PMO 自己跑完抓信息 → 对进度 → 报风险 → 出简报这一整条链路，人只做最后确认这一步。

§ 04

产品定位（一句话）

一句话价值主张 超体 PMO 不是又一个项目管理软件，而是装进超体 Skills 市场的第一个企业级 Skill：一位坐在你数据流里的 AI 项目经理，你不用再一个个去问进度，它会主动告诉你今天该操心什么。
§ 05

产品形态

超体 PMO 不是独立 App，而是Agent 加 Skills 市场的组合：用户在 Web 端有一个 PMO 工作台，背后是多智能体在跑，每个能力都以一个 Skill 的形式注册、接入、授权、调用。

这个设计正好对上这个岗位的核心命题：从 0 到 1 搭一个企业级 AI Skills 市场。PMO 是市场里的第一个旗舰产品（Flagship Skill），用它既验证产品是不是刚需，也顺便把 Skill 接入、质检、分发这条路完整跑一遍。

§ 06

多智能体架构

沿用 LangGraph 的多智能体编排，走 Orchestrator 统筹、专职 Agent 分工的 DAG 结构，每个专职 Agent 都能单独升级、单独挂 Skill。

§ 10

专有资产与竞争壁垒

产品底座可以开源，但真正的壁垒在「专有资产」——分三层，别人抄不走。
资产层内容可复制性定位
开源底座LangGraph / MinerU / Milvus / 飞书 MCP人人可装落地可行性，非壁垒
自研 Skillprompt-forge · prism-review · token-warden · slide-smith 等 80+ / 120+ Prompt难（招牌 Skill + 领域 know-how）能力差异化
私有数据 / 规则风险规则库、评测集、badcase 库、few-shot 样例极低（含商业机密、随数据迭代）核心护城河

壁垒的成立靠四类「别人抄不走」的东西，而不是「代码不公开」这一个动作：

  • 场景规则库：针对创始人/私募人群的风险规则——「负责人沉默 > 48h 判停滞」「里程碑连续变更 3 次判范围蔓延」——这是领域 know-how，不是代码。
  • 评测集与 badcase 库：在真实企业数据上迭代出的 QA 数据集与对抗样例，不公开、含商业机密。
  • Prompt 与 few-shot 工程：grill-me 的对抗话术、caveman 的压缩风格，是反复调优沉淀，抄不走。
  • 编排模式：多 Agent DAG + 人工「收口确认」节点的架构设计 know-how。
壁垒的正确打开方式（重点） 竞争力的来源是「专有 + 随数据持续演进」的规则与评测资产，而不是「不维护就不可用的黑盒」。前者让对手抄不走、让产品离不开这套沉淀；后者会被解读成单点依赖风险，反成减分项。

§ 11

需求详情

六项核心功能，每项遵循「触发器 → 处理规则 → 输出结果 → 状态变化」的完整链路。
1
上下文自动接入（零录入）
P0

管理者最顽固、最深的痛点是信息太散、又没人愿意录。RetrievalAgent 只读接入飞书群、邮件、日历和文档，自动抽跟项目有关的信号：谁提了里程碑、谁更新了进度、哪场会议的结论跟交付有关。

触发器：数据源产生增量（新消息、新邮件、日程变更、文档更新）。处理规则：Agent 做实体识别与项目归属判定，将零散文本抽取为结构化信号（项目、里程碑、责任人、动作、时间），写入企业语料库；无法判定归属的信号进「待归类」队列而非丢弃。输出：项目页「上下文流」。状态变化：未处理 → 已抽取 → 待关联/已关联。

权限上，RetrievalAgent 仅申请只读权限，且用户可关闭任意数据源。这是「零录入」体验的根基，也是产品与通用 PM 工具最大的分野。

2
进度追踪与停滞识别
P0

StoryboardAgent 持续对比计划和实际，识别延期与停滞。它不让负责人手动报进度，而是从上下文信号里反推实际进度，再跟里程碑计划算偏差。

触发器：里程碑到期临近，或某环节超过设定阈值（如 48 小时无新信号）仍无进展。处理规则：计算偏差率；容差内「正常」，超出「关注」，连续停滞超阈值升级「停滞」。输出：健康度条形图 + 「计划 vs 实际」分项。状态变化：正常 → 关注 → 停滞 → 已干预。

停滞识别是 PMO 价值的核心，因为它把「负责人沉默」这种最隐蔽的风险显性化了——这正是创始人最需要的「有人替我看门」。

3
风险预警与主动推送
P0

RouterAgent 识别阻塞、责任人不明、交付延迟、范围蔓延四类风险信号，主动推到工作台“今日该你操心”那一栏，而不是等着用户打开系统自己找。

触发器：任一风险信号被命中。处理规则：按影响面 + 紧迫度评估风险等级（高/中/低），召回优先（宁可多报不漏报），低置信风险进「观察」而非直接推送。输出：风险卡片，含风险说明 + 信号源 + 建议动作。状态变化：预警 → 已读 → 已分配 → 已闭环。

每日主动推送的「待操心事项」上限为 3 条，避免把创始人重新淹没在提醒洪流里——克制本身就是产品设计。

4
决策简报与周报生成
P0

ScreenwriterAgent 把多个项目的状态、风险、待拍板事项，压成创始人看得完的三句话简报和周报。输出按结论先行、证据支撑、待决策项这个顺序来，而不是堆数据。

触发器：用户请求或定时（每日早间、每周一）。处理规则：聚合各 Agent 输出，按重要性排序，套用 caveman 式压缩风格削减冗余；所有结论必须携带来源引用，无法溯源的推断不得进入简报。输出：一键转为文档/消息，发送前经 QCAgent 核查。状态变化：草稿 → 待核查 → 待确认 → 已发送。

对 P0 用户而言，简报是产品的「最后一百米」——它必须可溯源、可点击下钻，避免变成一个「看似聪明但不负责」的黑盒。

5
Skills 市场与 Skill 订阅
P0

市场的核心是让用户像开订阅一样按需接入 Skill，而不是一下买一堆功能。PMO 的能力拆成 progress-tracker、risk-scanner、brief-generator 这些 Skill，每个都能单独开关、单独授权。

触发器：用户浏览市场、点击「接入」某个 Skill。处理规则：弹出授权页，明确列出该 Skill 需要读取的数据源与权限范围，遵循最小权限原则；授权后 Skill 立即进入 Agent 的可调用工具集。输出：工作台出现该 Skill 对应的 Agent 模块。状态变化：未接入 → 待授权 → 运行中 → 已停用。

这一设计让「企业级 Skills 市场」从一个概念，落成一个可增长的商业模型：每个 Skill 都是可计费、可分发的资产。

6
质检红队（防幻觉）
P1

企业场景对可信的要求近乎苛刻。QCAgent 复用 grill-me 跨模型对打的思路，对 ScreenwriterAgent 的每一份输出做逐条溯源，防止模型把猜测当成事实写进简报。

触发器：ScreenwriterAgent 产出简报。处理规则：逐条校验结论是否有来源引用；置信度低于阈值的条目被拦截，标注「需人工确认」而非直接删除。输出：通过 / 拦截清单。状态变化：待核查 → 通过/拦截 → 人工复核。

这一步虽然增加延迟，但它是产品面对高净值用户时建立信任的护城河——一次错误的汇报，代价远高于一次延迟。

二、AI 专项指标与降级

作为 AI 产品，必须显式定义质量目标（数值为初期预估，标注 [待上线校准]）：

指标目标值降级机制
风险预警召回率≥ 95%（不漏报优先）低置信风险转「观察」，人工抽查
简报幻觉率< 1%无来源引用条目一律拦截

三、权限与数据隔离

面向企业/高净值用户，数据安全是底线。所有 Skill 遵循最小权限 + 只读优先；企业语料库按租户隔离；Agent 调用全程留痕（trace / metrics / logging），支持审计回溯。

四、监督 Agent 与止损机制

PMO 能稳定跑，不是靠相信每个 Agent 都不出错，而是靠一个横切的监督 Agent（BadcaseAgent）在边界兜底。它盯着所有执行 Agent 的心跳和输出，抓卡点（没进展）和报错（异常、幻觉），再触发分级降级与止损。

4.1 监督 Agent 如何设置

BadcaseAgent 不干业务，只做三件事：① 心跳监控，每个子 Agent 在 LangGraph 节点里注册心跳，由它记录执行时长，超时就判卡点；② 错误捕获，拦下基础设施错误（API 超时、限流）、模型错误（幻觉、低置信）和编排错误（死循环、依赖缺失）；③ 分级响应，按下面的表把异常映射到对应的止损动作。

4.2 卡点 / 报错的分级应对

级别异常表现应对方案止损动作
L1数据源暂时不可用（飞书/邮件 API 超时、限流）指数退避重试 3 次仍失败则该源标「暂停」，用缓存兜底
L2单节点超时 / 卡点（某 Agent 超阈值无进展）中断该节点，重启一次二次卡点则跳过该节点，降级输出并标注
L3输出置信度不足（幻觉、无来源引用）QCAgent 拦截，不进简报转「待人工确认」，绝不静默丢弃
L4编排级循环（状态机死循环、依赖缺失）Orchestrator 熔断，回滚检查点回滚到最近检查点，保留上下文
L5全局故障（模型服务整体不可用）切换备用模型 / 备用路由降级到「只读汇总」，暂停主动推送

4.3 亏损最低化策略

这里的亏损其实是两笔账：一笔是钱的亏损（token、API 调用），另一笔是机会的损失（漏报风险，错过干预窗口）。止损的关键是按风险分层，把贵的算力花在刀刃上，靠下面四条：

  • 模型分级路由：抽信号用小模型（便宜），风险研判用大模型（贵但值得），只在「中置信」时才加跑贵模型——昂贵计算只花在关键判断上。
  • 缓存与去重：上下文抓取去重、RAG 检索结果缓存，压掉重复 API 调用。
  • 熔断阈值：设单任务 token 上限与单日调用次数上限，超限自动降级而非无限重试。
  • 漏报优先的止损权衡：对高净值用户，漏报的代价（「为什么不早告诉我」）远高于误报（多打扰一次），所以低置信不直接砍掉，而是进「观察队列」承接——这是定义清楚「亏损」后的策略选择，而非一味节约。

五、边界与非目标（本期不做）

  • 通用项目管理的工时、甘特图、复杂看板不做——这些已有成熟工具，而且它们正是要人喂数据的那类失败样板。
  • 自动执行决策（自动发邮件、自动批准）不做——PMO 只给建议，最终动作必须人来确认。
  • 面向个人的娱乐化 Agent 市场不做——这期只做企业级、高净值场景。

六、开放问题

  • 「零录入」体验是否会让用户产生「看不见 Agent 在工作」的信任疑虑？[待用户访谈验证]
  • 飞书/邮件等数据源的接入授权，是否需逐企业申请商业 API 权限？[待技术确认]
  • PMO 的定价锚点：作为超体会员增值，还是独立订阅？[待商业评估]

POST 01 Harness · 驾驭系统

公司半年上了 7 个 AI 工具，月账单 20 万，效率反而降了——直到我做了这件事，一键全收编

备选 1：「花 50 万上 AI，结果更乱了——90% 的公司，第一步就走错了」
备选 2：「7 个 AI 工具 = 7 个数据孤岛？我用一张图，3 天把混乱清零」
备选 3：「别再给公司买 AI 工具了——你在给未来的混乱买单」

微博锚点（来自《超体》邀请信原文）

「AI 是一个巨大无比的放大器。但正因如此，它可以把你本身的混乱和模糊放大 100 倍。这就是为什么有很多人感知到 AI 非常好用，但是越用越累，不仅没有让自己的生活和工作变得更轻松，反而有种被 AI 吞噬的感觉。而要学会 harness 自己，你必须回到和 AI 这个神经系统对应的，你自己的神经系统。」

前沿信息
  • OpenAI：GPT-5.6 Sol 加了「思考量滑块」和 Ultrafast 模式（14 倍速、750 token/s）——AI 越来越强，但也越来越容易「用力过猛」，把企业的流程问题放大。
  • Anthropic：Claude Opus 5 主打「thoughtful and proactive」，企业客户开始用它做全流程自动化——但很多公司发现，自动化了以后，错得更快了。
  • X 热议：「AI 落地失败的第一原因不是技术，是组织」——这是 X 上 8 月企业 AI 圈最热的一条帖，下面有几百条 CIO 留言吐槽：工具买了一堆，流程没改，结果就是混乱 × 10。
企业落地场景
落地场景 · 企业 AI 落地治理框架 一家 300 人的科技公司，半年内上了 7 个 AI 工具，结果各部门各用各的，数据不通、prompt 乱传、有人拿核心数据喂公共模型。解法是搭一套「Harness 体系」：① Harness Self（组织端）——先梳理清楚哪些流程该 AI 化、哪些不该，画一张「AI 权限地图」；② Harness AI（工具端）——统一接入层、统一模型路由、统一数据安全策略；③ 人机分工（边界端）——明确什么 AI 能直接做、什么必须人审核。三个月后，AI 工具从 7 个收敛到 3 个，但实际产出翻了 2 倍。
内容大纲
  1. 开场：一个扎心的普遍现象

    X 上一位 CTO 说：我们公司上了 AI 以后，效率没提多少，混乱翻了倍。每条业务线都在买 AI 工具，每个人都在用不同的 prompt，数据散在七八个平台里——AI 没帮上忙，先把组织的混乱全放大了。

  2. 丹尼的洞见：Harness Self 比 Harness AI 更重要

    在超体邀请信里，丹尼把这件事讲得很透：AI 是放大器，你本身乱，它就让你更乱。个人如此，企业更如此。大部分企业做 AI 落地，上来就买工具、选模型，却从不问一个更基础的问题：我们自己的系统理顺了吗？

  3. 企业版的 Harness Self 是什么

    个人的 Harness Self 是管好自己的神经系统、注意力、能量；企业的 Harness Self 是管好自己的流程系统、数据系统、决策系统。AI 不是来替代这些系统的，是来增强它们的——系统没搭好，AI 只是加速器，加速混乱。

  4. 怎么搭：三层 Harness 框架（直接能用）

    ① 治理层：谁能用 AI 做什么、不能做什么，画一张清晰的权限地图；② 工具层：统一接入、统一路由、统一安全，不让各部门各买各的；③ 流程层：每个业务场景先画「人机分工图」，再上 AI。X 上有人开源了这套框架模板，一周内拿到了 3000 多 Star。

  5. 一个反直觉的结论

    企业 AI 落地的第一个动作，不是买工具、招算法工程师，而是先把自己的流程画出来。画不清楚的流程，上了 AI 只会更乱。

AI 不是答案，是放大器。你问对了问题，它让你飞；你本身乱，它让你更乱。

POST 02 Vibe Coding · AI 原生工作流

CEO 在手机上敲了 3 句话，一个 App 就做好了——这不是科幻，是 vibe coding

备选 1：「运营岗不会写代码，靠一句话自己搭了个数据看板——每个员工都是一支开发团队」
备选 2：「不用等 IT 排期了——我让运营自己搭工具，效率翻了 3 倍」
备选 3：「丹尼说第一节课就能当程序员，我以为是吹牛——直到我用手机做了个工具」

微博锚点（来自《超体》邀请信原文）

「他是一个日消耗 5 亿 token 以上的 vibe coder，但他完全不是程序员出身。」「Vibe Coding 只是手。Harness AI 是脑。Harness Self 是神经系统。」「第一节课后，你就能成为一个程序员，你就能够开发出人生中第一个程序。不需要你有任何程序员背景、理科生背景。」

前沿信息
  • OpenAI：Codex 电脑客户端 + iPhone Remote 版上线，让「用自然语言写代码」从桌面延伸到手机；GPT-5.6 Sol 在代码任务上的能力大幅提升，非程序员也能搭完整应用。
  • Anthropic：Claude Code Security 上线，能扫描代码库漏洞并给出补丁——代码 AI 已经从「写代码」进化到「审代码」，意味着非程序员也能做过去要团队做的事。
  • X 热议：「Vibe Coding 会不会让 80% 的程序员失业」在 X 上吵了整整一周。但更有意思的一个观点是：失业的不是程序员，是不会 vibe coding 的知识工作者——因为未来每个人都得会「用描述造工具」。
企业落地场景
落地场景 · 全员 AI 原生工作流改造 一家消费品公司的运营团队有 12 个人，一半不会写代码，但每天要处理大量数据报表、用户反馈、营销素材。他们做了一件事：全员 vibe coding 培训——不是教编程，是教「怎么用自然语言让 AI 给你造工具」。两个月后：① 运营自己就能搭数据看板，不用等数据团队排期；② 用户反馈自动分类 + 生成回复建议，效率翻 3 倍；③ 有个文案甚至自己搭了一个 A/B 测试小工具。最关键的是——他们没有招一个程序员。
内容大纲
  1. 开场：丹尼的 5 亿 token 是什么概念

    一个人一天消耗 5 亿 token——这大概相当于一个中型开发团队一周的用量。但丹尼不是程序员，他是乐纯的 CEO。这件事本身就意味着：写代码这件事，正在从「专业技能」变成「基本能力」。

  2. 什么是 Vibe Coding：不是写代码，是「描述你要什么」

    传统编程是告诉电脑「怎么做」，vibe coding 是告诉 AI「我要什么」。这个转变的意义不亚于从汇编语言到高级语言的跃迁——它让造软件这件事，第一次向非程序员敞开了大门。

  3. 但丹尼说得更狠：Vibe Coding 只是手

    真正重要的是 Harness AI（脑）和 Harness Self（神经系统）。也就是说，会不会描述是一回事，知道该描述什么是另一回事。很多企业的误区就是：以为让员工学会用 AI 写代码就够了，其实更重要的是让员工知道「该让 AI 做什么」。

  4. 企业怎么落地：全员 AI 原生工作流改造路径

    ① 先选一个试点部门（运营/市场/HR），找 3-5 个高频痛点；② 用 vibe coding 快速做 3 个小工具，让大家看到效果；③ 总结成「部门 AI 工具包」，推广到全公司；④ 建立内部「AI 工匠」机制——每个部门出一个人，专门负责攒工具、分享方法。

  5. 一个判断

    未来 3 年，不会 vibe coding 的知识工作者，就像今天不会用 Excel 的人一样罕见。区别只在于，你是主动升级的那批，还是被动淘汰的那批。

未来不是程序员统治世界，是会「描述」的人统治世界。

POST 03 能量 · 终极货币

CEO 每天只看 3 条手机推送，公司反而跑得更快——丹尼「能量货币论」的企业版实践

备选 1：「我把 CEO 60% 的工作扔给了 AI，他每天多出来 5 小时，只干一件事」
备选 2：「别再搞时间管理了——真正厉害的 CEO，都在管理『能量』」
备选 3：「每月花 2000 块买 AI，换 CEO 每天 3 小时深度思考——这笔账太值了」

微博锚点（来自《超体》邀请信原文）

「人生的终极货币，是你每天的能量（Energy）。」「Harness AI = 因为 AI 的能量很简单，就是不断扩充电力和算力，所以 AI 第一次让普通人，可以用极其低廉的价格，实现自身能量的无限扩展。你只要理解 Human Being 和 AI 在神经系统的差异，就能高效做能量的分工，从而最大化自身可调用的能量。」

前沿信息
  • OpenAI：GPT-5.6 Ultrafast 模式 14 倍速、750 token/s——AI 的「能量输出」正在指数级增长，而且越来越便宜。
  • Anthropic：Claude Fable 5 全渠道上线（Bedrock / GitHub Copilot / API），企业可以随时调用「最强脑力」，成本只有人类专家的几十分之一。
  • X 热议：「企业 AI 的 ROI 计算公式是错的」——X 上一位创业者的帖子引爆了讨论。大部分公司算 AI 的 ROI 是「省了多少人力成本」，但真正的 ROI 是「释放了多少高价值人才的能量」。两种算法，差了一个数量级。
企业落地场景
落地场景 · 创始人 / 高管「能量释放」工程 一位 CEO 每天工作 12 小时，但其中 60% 的时间花在了读邮件、回消息、看报表、追进度这种「低能量决策」上——真正用来想战略、做关键判断的时间不到 20%。解法是做「能量分级工作流」：① 把他的日常任务按「能量等级」分类（L1 机械回复 / L2 信息汇总 / L3 判断决策 / L4 战略思考）；② L1 和 L2 全部交给 AI Agent 处理，他只看结论；③ L3 保留人做决策，但 AI 提前准备好所有背景材料和选项；④ L4 每天保证至少 3 小时不被打扰的深度工作时间。三个月后，他的战略思考时间从 20% 升到了 50%，公司关键决策的质量明显提升——而这一切的成本，就是每月两千多块的 API 费。
内容大纲
  1. 开场：丹尼的「能量货币论」

    丹尼在超体邀请信里说：时间不是终极货币，注意力也不是，能量才是。因为同样的 24 小时，高能量状态和低能量状态下的产出，可能差 10 倍。这个道理放在个人身上成立，放在企业身上更成立。

  2. 企业最大的浪费，是 CEO 能量的浪费

    X 上有个调研扎心：平均下来，创始人 60% 的时间花在「不需要他做、但别人又做不了那么快」的事情上——回邮件、看报表、开会对齐、追进度。这些事不是不重要，但它们消耗的是一个组织最贵的能量。

  3. AI 的真正价值：不是替代人，是「能量平移」

    大部分公司算 AI 的 ROI 都算错了。他们算的是「AI 替我做了几个人的活，省了多少钱」。但真正的 ROI 是：AI 把高价值的人从低价值的事里解放出来，让他们把能量用在真正重要的地方。这两种算法，差了至少一个数量级。

  4. 怎么落地：「能量分级」工作法（创始人 / 高管版）

    ① 先做一周的「能量审计」——记录每天每个小时在做什么、属于哪个能量等级；② 按 L1–L4 分级，L1 和 L2 全部外包给 AI；③ 给 L3 和 L4 留足「不被打扰的时间块」；④ 每月复盘，持续把更多任务往下移。这不是时间管理，这是能量管理。

  5. 收尾：回到超体的那句话

    「Harness AI 实现自身能量的无限扩展。」对个人来说，这是 10 倍生产力的来源；对企业来说，这是下一个 10 年的核心竞争力——谁先把最贵的人的能量，用在最贵的地方，谁就赢。

企业和企业的差距，归根到底是能量使用效率的差距。

B

SaaS 创业公司 · CEO 多项目并行

目标用户：P0 创始人 / CXO
痛点：产品、销售、融资三条线并行，信息全在飞书群和 Linear 里。CEO 每天花 1-2 小时「刷群 + 追进度」，最痛的是不知道「哪条线今天必须我拍板」。
落地路径
  1. larksuite/lark-openapi-mcp 只读接入飞书消息与日历，Linear MCP 接入研发进度。
  2. RetrievalAgent 抽取「@ 老板」「等待确认」「blocker」相关的信号，做项目归属判定。
  3. StoryboardAgent 比对 Linear 的 Cycle 进度和飞书里的口头承诺，识别「进度撒谎」和「隐性停滞」。
  4. RouterAgent 按影响面 + 紧迫度排序，每日只推 3 条「今日该你操心」。
  5. ScreenwriterAgent 生成结论先行的三句话简报，附来源链接，QCAgent 拦截无溯源条目。

C

消费品牌 · 供应链履约追踪

目标用户：P1 管理者 / 项目负责人（参考乐纯母公司场景）
痛点：供应商排期、生产、渠道上架是一个长链路，涉及多方协作。延期常有「人没报、也没人追」，等发现时已经错过档期。
落地路径
  1. 钉钉 MCP（china-mcp-servers）接入供应商沟通群，Notion MCP 接入项目台账。
  2. RetrievalAgent 从群聊里抽取「交期」「排产」「上架」等履约关键词，建立履约时间线。
  3. StoryboardAgent 对每个履约节点做「计划 vs 实际」比对，超阈值标记「关注/停滞」。
  4. RouterAgent 识别「责任人不明」的节点（谁都没接的活），主动提醒。
  5. 周报由 ScreenwriterAgent 自动汇总，替代人工周会时的逐条对齐。

预期产出：延期从「事后才发现」变成「提前 14 天预警」，周会从 60 分钟缩短到 15 分钟。

落地技巧（为什么这套清单可信）

  • 优先选官方或 30k+ Star的成熟项目（larksuite 官方 MCP、MinerU、LangGraph、Milvus），避免接一个没人维护的小仓库。
  • 中国企业首选 china-mcp-servers 这类中文生态合集，一次覆盖飞书+钉钉+企微，而不是每个平台单独找。
  • 全套组件都是可私有化部署的，数据留在客户侧，符合高净值用户对数据安全的底线要求。
  • 选择器细节不等于产品价值——这套清单的价值在于证明「每个能力都有成熟开源底座可承接」，落地风险低。
